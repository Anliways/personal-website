# 个人项目的微服务边界

微服务不是大型公司的专利，但**个人项目更容易犯「过度拆分」的错误**。分享几条我踩坑后的判断标准。

## 什么时候该拆

- 两个模块的**部署节奏**明显不同（例如高频迭代的通知服务 vs 稳定的存储服务）
- 某个模块需要**独立扩容**（如图片压缩、AI 推理）
- 技术栈差异大到强行统一反而增加复杂度

## 什么时候不该拆

- 团队只有你一个人，拆分带来的运维成本远超收益
- 模块间共享同一份数据模型，拆开只会制造同步地狱

## 我的实践

目前我的个人后端保持「一大两小」：主 API 单体 + 两个独立 Worker（自动化任务与媒体处理）。用 Docker Compose 编排，够用、够稳、够简单。

> 架构是权衡的艺术，而不是模式的堆砌。
